# 周报生成 SOP

## 注释要求

- 涉及生成或修改代码时，每个函数 / 方法都必须添加注释，说明其功能和适用场景。
- 关键业务流程、复杂分支、异常处理、副作用、并发、权限、外部调用等关键部分必须添加必要注释。
- 新增或修改的代码注释统一使用英文；注释格式沿用目标文件已有风格，保持简洁准确，避免重复描述代码本身。
- 修改代码时保留已有注释，不翻译或移动与本次修改无关的注释。

> 当用户提出“写周报”、“整理本周工作总结”、“生成周工作汇报”、“按固定格式输出下周计划”等请求时使用。

## 核心原则

1. 先收集关键信息，再生成周报；关键字段缺失时，禁止直接输出成稿。
2. 仅基于用户提供的事实和上下文整理内容，不编造完成项、量化结果、截止日期、风险或支持诉求。
3. 输出必须严格遵循固定模板与章节顺序，不新增、不删减、不改名。
4. 文本风格保持客观、简洁、可直接复制发送；每条尽量使用“事项：结果/影响”的句式。
5. 用户原文中的系统名、分支名、环境名、缩写和技术术语保持不变。
6. 当用户已给出“本周完成”或自然语言总结时，应优先自动归纳“量化结果”，仅在确实无法归纳时再追问。
7. 当用户未提及风险 / 阻塞、需要支持时，默认输出 `* 无`，不额外追问。
8. 当用户未提供姓名时，默认填写 `孙亮`。
9. 当用户未提供周期时，默认填写 `2026-W17`。
10. 当用户未提供下周计划 DDL 时，使用模板值 `YYYY-MM-DD` 占位，不额外追问日期。

## 强制字段

| 编号 | 字段 | 要求 |
|:---:|------|------|
| WS-01 | 姓名 | 选填；用户未提供时默认写 `孙亮` |
| WS-02 | 周期 | 选填；用户未提供时默认写 `2026-W17`，建议格式 `YYYY-Www` |
| WS-03 | 本周完成 | 必填，1~3 条 |
| WS-04 | 量化结果 | 必填，优先输出 3 条；应先根据用户本周总结和上下文自动归纳，无法归纳时再追问 |
| WS-05 | 下周计划 | 必填，1~3 条；每条都带 `DDL`，用户未提供日期时填模板值 `YYYY-MM-DD` |
| WS-06 | 风险 / 阻塞 | 必填；用户未提及时默认写 `* 无` |
| WS-07 | 需要支持 | 必填；用户未提及时默认写 `* 无` |

## 步骤 1：信息自检

收到用户输入后，先判断以上字段分别属于：
- 已知
- 缺失
- 可直接从上下文整理

若 `WS-01` 缺失，默认填 `孙亮`，不追问。

若 `WS-02` 缺失，默认填 `2026-W17`，不追问。

若 `WS-04` 缺失，但可根据 `WS-03` 或上下文自动归纳，则先归纳，不追问。

若 `WS-05` 缺少 DDL，仅为缺少日期时，保留计划事项并将 DDL 填为 `YYYY-MM-DD`。

若 `WS-05` 整体缺失，不得直接生成最终周报。

若 `WS-06`、`WS-07` 缺失，默认填 `* 无`，不追问。

## 步骤 2：结构化追问

若信息不完整，按以下方式一次性追问缺失项，避免来回拉扯：

```markdown
在生成周报前，我需要你补充这些信息：

1. 姓名和周期
   姓名未提供时默认使用 `孙亮`；周期未提供时默认使用 `2026-W17`
2. 本周完成
   最多 3 条，每条说明“做了什么 + 结果”
3. 下周计划
   最多 3 条；若未提供截止日期，我会先用 `DDL：YYYY-MM-DD` 占位
```

如果用户已经给出了自然语言描述，但不够结构化，应先帮用户归并，再只追问缺失项。

若量化结果可从用户本周总结、上下文、已给出的交付件/数量/阶段状态中自动整理，则不要单独追问量化结果。

## 步骤 3：整理规则

### 3.1 本周完成
- 最多保留 3 条，优先保留业务价值最高、对外可汇报的事项。
- 每条聚焦“动作 + 结果”，避免流水账。
- 可将多个零散动作合并为一条，但不能改变事实。

### 3.2 量化结果
- 必须有该章节。
- 优先输出 3 条，并使用 `指标1`、`指标2`、`指标3` 编号。
- 默认从 `本周完成` 和上下文自动归纳，不要求用户单独提供。
- 自动归纳时，只能做事实压缩和结果提炼，不能虚构数字或未发生的收益。
- 优先提取以下信息形成量化结果：
  - 明确数量：接口数、需求数、缺陷数、文档数、脚本数、页面数、任务数
  - 明确状态变化：未完成 -> 已完成、手工 -> 自动化、未上线 -> 已上线、未覆盖 -> 已覆盖
  - 明确阶段推进：完成开发、完成联调、完成测试、进入灰度、进入验收
  - 明确范围变化：支持某模块、覆盖某场景、打通某链路、收敛某类问题
- 可接受的表达包括：
  - 问题现状 -> 当前结果
  - 旧方案 -> 新方案
  - 未覆盖 -> 已覆盖
  - 未完成 -> 已完成 / 进入某阶段
- 若用户只提供了定性描述，也应优先改写为“动作 + 结果”的可验证表述，例如：
  - “完成 A 功能开发” -> “A 功能完成开发并提测”
  - “优化 B 流程” -> “B 流程由手工处理收敛为标准化流程”
- 只有在连“状态变化 / 覆盖范围 / 交付结果”都无法从上下文归纳时，才追问，不得自行编造。

### 3.3 下周计划
- 最多保留 3 条，按优先级排序。
- 每条都要落到明确动作，并附 `DDL`。
- 若用户未提供日期，默认补为模板值 `DDL：YYYY-MM-DD`。
- 若用户只给“下周继续跟进”这类模糊描述，必须追问具体事项；日期可先不追问。

### 3.4 风险 / 阻塞
- 用“现状：影响：预计解除时间”或接近的表达整理。
- 如用户明确没有风险，输出 `* 无`。
- 如用户未提及风险，也直接输出 `* 无`。

### 3.5 需要支持
- 优先写清楚“需要谁支持 + 支持什么 + 最晚时间”。
- 如用户明确没有支持诉求，输出 `* 无`。
- 如用户未提及支持诉求，也直接输出 `* 无`。

## 步骤 4：固定模板输出

生成最终结果时，只输出周报正文，不加解释、不加前言、不附额外说明。

````markdown
#周报
姓名：{姓名，未提供时默认孙亮}
周期：{周期，未提供时默认2026-W17}

1) 本周完成（最多3条）
* {完成1}
* {完成2}
* {完成3}

2) 量化结果（必须）
* 指标1：{量化结果1}
* 指标2：{量化结果2}
* 指标3：{量化结果3}

3) 下周计划（最多3条，带截止日期）
* {计划1}（DDL：{日期1或YYYY-MM-DD}）
* {计划2}（DDL：{日期2或YYYY-MM-DD}）
* {计划3}（DDL：{日期3或YYYY-MM-DD}）

4) 风险 / 阻塞
* {风险1}
* {风险2}

5) 需要支持
* {支持1}
````

## 步骤 5：输出约束

- 第一行必须是 `#周报`，不要写成 `# 周报`。
- 标题和章节名称必须与模板完全一致。
- 使用 `* ` 作为条目符号。
- 保留用户提供的日期、分支名、环境名、系统名与英文术语。
- 若某章节只有 1~2 条，按实际条数输出，不补空白占位。
- 若用户要求“润色”、“更正式”、“更简洁”，只能调整措辞，不能新增事实。

## 推荐话术

### 用户信息不足时
- “为了按固定格式生成周报，我还缺少几个必填信息：下周计划事项。姓名我会默认写孙亮，周期我会默认写 2026-W17，DDL 会先用模板值补齐。”
- “你已经给了本周完成项，我会先自动整理量化结果；如果下周计划没写日期，我先用 `DDL：YYYY-MM-DD` 占位。”

### 用户信息完整时
- “我会按你提供的信息直接整理成可发送的周报文本。”

## 避免事项

- 不要把聊天解释、分析过程或建议混进周报正文。
- 不要把“可能”、“预计”、“应该”等猜测当成既成事实。
- 不要擅自补充未提供的具体数字、日期、风险或支持对象。
- 不要因为姓名、周期或 DDL 日期缺失而重复追问；应分别使用默认值 `孙亮`、`2026-W17` 和 `YYYY-MM-DD`。
